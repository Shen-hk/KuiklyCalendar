# 技术调研与选型报告

## 参考结论

- Issue 指定的 [KuiklyChatUI](https://github.com/Kuikly-contrib/KuiklyChatUI) 采用 `ViewContainer` 扩展函数作入口、DSL 配置、主题对象、Slot 优先级和可直接运行的 Mock/Demo；本组件沿用这一接入模式，但不复制聊天组件的复杂工厂体系。
- [react-native-calendars](https://github.com/wix/react-native-calendars) 的核心经验是：日期标记、主题、禁用日期、相邻月和可定制日单元格应彼此独立。其月历支持点、多点、区间等标记；本次先实现轻量的 1～3 色点，保留 `CalendarMarker` 可扩展入口。
- [Flutter table_calendar](https://pub.dev/packages/table_calendar) 将 `focusedDay`、`selectedDay`、日期边界、事件加载和 selective builder 分离。本组件对应为 `currentMonth()`/`showMonth()`、`currentSelection()`/`select()`、`minDate/maxDate`、`markers`、`dayContent`。

## 方案对比

| 方案 | 性能与包体 | 跨端一致性 | 侵入性/维护 | 结论 |
| --- | --- | --- | --- | --- |
| A：组合现有 `DatePicker` | 包体最小 | 只能滚轮选日，不能满足月格布局 | 低，但无法形成日历组件 | 放弃 |
| B：`commonMain` ComposeView + 纯 Kotlin 网格算法 | 固定 42 个轻量节点，无新依赖 | 高，所有端共用同一算法 | 低，符合 Kuikly 原生范式 | 采用 |
| C：各端原生日历/原生扩展 View | 原生性能高 | 高定制时难保持一致 | 高，需 Android/iOS/OH/H5 多套实现 | 放弃 |

## 最终选型理由

方案 B 直接采用 Kuikly 的 `ComposeView`、`ComposeAttr`、`ComposeEvent`、`vbind` 与 `CalendarModule`。月份切换只重建 42 个单元格，不依赖网络、图片、原生扩展或第三方日期库。公历算法是纯 Kotlin，因此 H5 与移动端日期网格不会因宿主时区、`Date` API 差异而分叉。

## 风险与技术债取舍

- 组件没有内建无障碍语义桥接；这属于 Kuikly 渲染层能力，后续应在框架支持标签/role 时补充。
- `dayContent` 已提供高定制入口，但未开放“替换整个 Header”的插槽；当前需求只需月切换，先保证按钮、边界和回调一致。
- 范围选择和多选不应通过布尔开关临时拼接，后续应引入 `CalendarSelectionMode` 与独立 selection model，避免破坏单选 API。
